    Documentació tècnica

    Ona Bages Play · versió 0.1.0 · novembre de 2026

    Aquest document és per a qui instal·la i manté l'aplicació: com preparar l'ordinador, com està feta, com es compila i com s'hi afegeixen coses. És un resum. La referència detallada és als fitxers del repositori:

    • docs/especificacio.md: què ha de fer l'aplicació i per què.
    • docs/protocol.md: totes les ordres i els esdeveniments entre la interfície i el motor.
    • docs/decisions.md: registre de decisions (D-001, D-002…), amb el motiu de cadascuna.
    • CLAUDE.md: les regles del projecte (arquitectura, motor, enregistrament, interfície, dades).

    Prioritat absoluta: l'àudio no es pot interrompre i els enregistraments no es poden perdre. Qualsevol canvi s'ha de valorar primer amb aquesta regla.

    Preparar Windows

    Molts talls d'àudio no els provoca l'aplicació sinó el sistema. A cada ordinador d'estudi (la llista completa, amb caselles per marcar, és a docs/installacio-windows.md):

    Dispositius de so

    Tauler de control > So (mmsys.cpl), pestanyes Reproducció i Enregistrament, a cada dispositiu que farà servir l'aplicació:

    • Millores i àudio espacial: desactivats.
    • Format predeterminat (Opcions avançades): el mateix a tots, per exemple 24 bits, 48000 Hz.
    • Creative (Sound Blaster): desactivar SBX, Crystalizer, equalitzadors i altres efectes a les sortides d'antena.
    • Realtek: desactivar la detecció de connectors si la consola ho permet. Amb els connectors del darrere, treure un cable fa desaparèixer el dispositiu: no s'han de tocar durant un programa.
    • So dels monitors (HDMI / DisplayPort): si no es fa servir, desactivar-lo a l'Administrador de dispositius (no n'hi ha prou amb el tauler de So). Si no, encendre o apagar el monitor fa perdre uns mil·lisegons d'àudio a totes les targetes.
    • Posar un nom clar a cada dispositiu («Antena 1», «Auriculars preescolta», «Taula PGM»…).

    Sistema

    • Sons del sistema: esquema «Sense sons». El dispositiu predeterminat de Windows no ha d'anar a antena.
    • Pestanya Comunicacions: «No fer res» (si no, Windows abaixa el volum quan detecta una trucada).
    • Desactivar les entrades de bucle que no es facin servir («Mescla estèreo», «Lo que se oye»).
    • Pla d'energia d'alt rendiment; suspensió selectiva USB desactivada; als concentradors USB, desmarcar «Permetre que l'ordinador apagui aquest dispositiu».
    • Windows Update: hores actives que cobreixin els programes. «No molestar» durant els programes.
    • Windows «N»: instal·lar el Media Feature Pack (sense ell no sonen els MP3).

    Inventari del maquinari

    tools/inventari.ps1 llegeix del registre tots els dispositius d'àudio i escriu una taula en Markdown. Només llegeix i no cal ser administrador:

    powershell -ExecutionPolicy Bypass -File tools\inventari.ps1 -Sortida docs\inventari

    Arquitectura

    Electron (app/) ── WebSocket 127.0.0.1 + testimoni ── Motor .NET (engine/)
  HTML + Bootstrap + JS pur                            NAudio (WASAPI) + LAME

    Dos processos separats:

    • Motor (engine/, C# / .NET 10): té tot l'àudio, tot l'estat i totes les màquines d'estats. És la font de veritat.
    • Interfície (app/, Electron): només mostra l'estat i envia ordres. Mai no reprodueix ni processa àudio.

    Per què separats: si la interfície es penja o es tanca, el motor continua sonant i enregistrant. En tornar a obrir-la, llegeix engine.json (port i testimoni), s'hi connecta i demana state.get per reconstruir la pantalla. Aquesta arquitectura no es canvia sense una decisió explícita.

    Cicle de vida

    1. Electron comprova si hi ha un motor viu (GET /health al port de engine.json). Si no, l'arrenca amb --port, --token i --data-dir.
    2. El motor: llegeix la configuració, crea els reproductors i enregistradors, compara el maquinari amb el desat, recupera els enregistraments interromputs (marcadors .rec) i escolta a 127.0.0.1.
    3. La interfície es connecta per WebSocket, demana state.get i a partir d'aquí s'actualitza amb els esdeveniments.
    4. En tancar: si no hi ha res actiu, engine.shutdown. Si n'hi ha, l'usuari tria tancar només la finestra (el motor continua) o aturar-ho tot (engine.shutdown amb force). El motor tanca primer els enregistradors, perquè els fitxers quedin bé.
    5. Canviar de perfil reinicia el motor amb el mateix port i testimoni (uns 3 s), i només es permet sense res actiu.

    Compilar, provar i empaquetar

    Cal: .NET 10 SDK, Node.js LTS i Git. No calen Visual Studio, MSVC ni CMake. Els passos detallats per clonar i preparar el projecte, i la resta d'ordres útils, són al README.md de l'arrel.

    # Motor
dotnet build engine/OnaBages.slnx
dotnet test engine/OnaBages.slnx
dotnet run --project engine/OnaBages.Engine -- --port 47800

# Interfície (des de app/)
npm install
npm start

# Desenvolupament (des de l'arrel): compila el motor i obre la interfície
.\arrencar.cmd

# Versió portable (des de l'arrel): build\OnaBagesPlay-<versió>.zip
.\empaquetar.cmd
    • Sense interfície: arrenca el motor i obre tools/consola-proves.html al navegador amb el port i el testimoni que mostra la consola. Permet enviar qualsevol ordre a mà.
    • Dades de proves: la variable d'entorn ONABAGES_DATA_DIR fa que Electron i el motor facin servir una altra carpeta de dades. Així es pot provar sense tocar la configuració real.
    • Proves automàtiques: unes 650, sobre la lògica (llistes, màquines d'estats, edició per fotogrames, recuperació, configuració, ordres) i sobre l'àudio amb senyals generats.
    • Proves d'àudio: OnaBages.ToneCheck genera un to de 1618 Hz, i un cop enregistrat l'analitza per detectar talls, clics o mostres perdudes. ToneCheck convivencia comprova que editar un fitxer d'una hora no afecta dos enregistraments simultanis.
    • Empaquetar: empaquetar.cmd publica el motor amb el .NET inclòs, empaqueta Electron amb @electron/packager, hi afegeix el motor (resources\engine), la carpeta dades, el LLEGEIX-ME.txt i la documentació (documentacio\), i ho comprimeix.

    El motor

    Fils i regles de l'àudio

    Cada reproductor, la preescolta i cada enregistrador tenen el seu propi flux WASAPI en mode compartit (100 ms, prioritat «Pro Audio»). Un error en un flux no afecta els altres.

    El fil d'àudio (les crides de NAudio/WASAPI) té regles estrictes:

    • no crea objectes, no bloqueja, no espera disc ni xarxa i no escriu registres;
    • només copia mostres d'una memòria intermèdia (SampleRingBuffer) preparada per un altre fil;
    • els mesuradors (PeakMeter) es guarden amb operacions atòmiques.

    La lectura dels fitxers i la codificació MP3 van en fils propis, amb segons de marge. Les excepcions es capturen per flux i es converteixen en un estat error amb un esdeveniment: el procés no cau mai per un error d'un flux.

    El motor fa una revisió cada 100 ms (final de pista, errors, posicions), envia els mesuradors 25 vegades per segon i desa les llistes i els recents que han canviat cada 2 s.

    Dispositius: s'identifiquen per l'id de Windows i, com a alternativa, pel nom. Mai no es fa servir el «dispositiu predeterminat» per a una sortida d'antena. Si en arrencar un dispositiu no hi és, l'element queda «Sense dispositiu»; no es reassigna mai sol a un altre (només es reassocia un dispositiu amb el mateix nom, si és únic).

    Reproductors i preescolta

    • Lectura: Media Foundation (MP3, AAC/M4A, WMA, FLAC…); WAV sense Media Foundation. Sortida sempre estèreo, remostrejada a la freqüència del dispositiu.
    • Cadena: fitxer → descodificació → guany de normalització → compressor/limitador → volum → fade-out → sortida. El fade-out (player.fadeOut, D-107) és un factor per mostra al fil d'àudio (constant en dB fins a −60 dB); quan acaba, Player.Tick fa el mateix que Stop.
    • Llista (Playlist): identificadors propis per element; la «pista següent» es calcula per identitat, no per posició, perquè la llista es pot editar mentre sona.
    • Encadenament: el fil de lectura decideix què ve després 1 s abans del final i continua escrivint a la mateixa memòria (sense silenci). El fos entre pistes es barreja al fil de lectura amb corbes d'igual potència.
    • Comprovació de pistes: TrackAnalyzer obre cada pista que s'afegeix, en mesura la sonoritat (EBU R128) i el silenci del principi i del final. Els resultats van a una memòria cau.
    • Preescolta (CuePlayer): un Player propi amb una llista d'una pista. No toca cap reproductor.
    • Historial del que ha sonat (PlayHistory): un CSV per dia, per a l'Excel en català (separador «;», UTF-8 amb BOM).

    Enregistradors

    • Captura WASAPI en float → memòria de 10 s → fil de codificació: volum → limitador opcional → LAME.
    • MP3 320 kbps CBR, sense etiqueta Xing/Info i sense bit reservoir: cada fotograma és independent, i el fitxer és vàlid en tot moment (també per tallar-lo a l'editor).
    • Un sol fitxer per enregistrament, amb Flush(true) (escriptura física) cada 2 s.
    • Marcador <fitxer>.mp3.rec mentre s'enregistra; s'esborra en aturar correctament.
    • Marques (recorder.mark, RecordingMarks): a <fitxer>.mp3.marques (JSON), mai dins de l'MP3. Es desen senceres a cada marca, des del fil de les ordres (no el d'àudio), i segueixen el fitxer en desar-lo, descartar-lo i a l'historial. A l'editor (EditorSession), el motor les passa a la versió editada amb els trossos que es queden (RecordingMarks.MapToEdited) i, en desar, les desa ajustades al costat del fitxer nou; la interfície només les dibuixa. «Desar la selecció» (editor.saveSelection) fa servir el mateix Mp3Edit.Save amb només els trossos de la selecció i no toca l'edició.
    • Noms i moure marques (D-114, D-115, D-118): recorder.nameMark hi posa nom (com a molt 60 caràcters) i editor.moveMark la mou; des de l'editor també se n'afegeixen, se n'esborren i se'ls posa nom (editor.addMark, removeMark, nameMark; D-125). Qui és l'amo de les marques: mentre un enregistrador enregistra o té el fitxer pendent, les marques són seves (Recorder.Marks, ordenades per temps); el router envia el moviment a Recorder.MoveMark i l'editor les torna a llegir (EditorSession.ReloadMarks). Si no, l'editor les canvia directament al fitxer .marques. Un sol lloc del router (MarksOwner) decideix qui és l'amo. Sempre es numeren per ordre de temps de l'original (1, 2, 3...), també després de retallar.
    • Alarma de silenci (D-121): el fil de codificació, just abans de LAME, mira si tot el bloc és per sota del llindar i suma o posa a zero un comptador atòmic (_silentFrames); Recorder.Tick (cada 100 ms) encén o apaga SilenceAlarm i avisa la interfície. Es mesura el que queda al fitxer, no el mesurador. Ajustos comuns del perfil (settings.silenceAlarm).
    • Historial d'enregistraments: el mateix fil escriu els mateixos bytes a una còpia (RecordingArchive). Un error a la còpia no afecta mai l'enregistrament principal.
    • Es compten les mostres perdudes i els avisos de Windows, i s'escriuen al registre amb la posició.

    Botonera d'instantanis

    • CartWall (D-127): sortida pròpia, sempre oberta (envia silenci), i 8 veus creades d'entrada. El fil d'àudio (CartWall.Mixer) barreja les veus actives en blocs de 20 ms, sense crear objectes.
    • Sona a l'instant: de cada botó es guarden els primers 3 s descodificats (LoadHead, en segon pla, a la freqüència de la sortida). En prémer-lo, la veu comença per aquesta memòria i un fil de lectura obre el fitxer just on s'acaba (AudioFileSource.Open(..., exactStart: true)) i omple la resta.
    • Fil de les ordres ↔ fil d'àudio: la veu es prepara i s'hi posa Active en últim lloc; el fil d'àudio posa Ended quan s'acaba o quan acaba el fos d'aturar, i Tick allibera la veu (atura el fil de lectura). Una veu només es torna a fer servir quan el fil d'àudio ja l'ha deixat.

    Processament (DSP)

    • Compressor/limitador (DynamicsProcessor): com el SqrSoft del Winamp, amb anticipació d'1,5 ms. El limitador dels enregistradors és el mateix amb ràtio 1 (només el sostre).
    • Normalització (Loudness): mesura LUFS de cada pista; el guany s'aplica a partir de la pista següent.
    • Retall de silencis: la pista s'obre al primer so menys un marge i el lector no dona més mostres que fins a l'últim so més un marge. El fitxer no es toca. Els espetecs aïllats (com a molt 20 ms) no compten com a so.
    • Els canvis de paràmetres s'apliquen amb rampa, sense clics.

    Editor

    • Sense recodificar: Mp3FrameIndex localitza cada fotograma; retallar o eliminar és copiar fotogrames sencers (~24–26 ms).
    • Fosos (Mp3Gain): es canvia el volum global de cada grànul en passos d'1,5 dB, com el mp3DirectCut. No es perd qualitat ni canvia la mida.
    • Normalització (D-123; EditorSession.Normalize, Mp3Edit.Gain): per pic. El pic surt de la forma d'ona (amb els fosos aplicats), sense descodificar; el guany és el mateix nombre de passos d'1,5 dB a tots els grànuls del fragment, arrodonit cap avall perquè mai no passi de l'objectiu.
    • Forma d'ona (WaveformPeaks): un pic per fotograma, calculat en un fil de prioritat baixa i desat a la memòria cau.
    • Desar escriu en un temporal i el substitueix. Si es desa a sobre de l'original mentre encara es calcula la forma d'ona, primer s'atura i s'espera el fil dels pics, que té el fitxer obert (D-116).
    • Enregistrament en curs (D-117–D-119): l'editor obre una fotografia del fitxer que creix (EditorSession.Open(path, live: true), Live): l'índex de fotogrames fins on era, sense memòria cau de pics. No en fa cap còpia ni hi escriu mai: Mp3Edit.Growing només comprova que el fitxer no s'ha escurçat, i Media Foundation el pot llegir encara que estigui obert per escriure. Es pot escoltar, seleccionar, moure marques i «Desar la selecció»; la resta d'ordres d'edició responen bad_state. editor.refresh torna a fer la fotografia; quan l'enregistrador s'atura, la interfície ho fa sola (recordings.changed) i el fitxer deixa de ser en directe.
    • Estat «ocupat»: les feines en segon pla (obrir, desar) netegen Busy en últim lloc, perquè qui llegeix l'estat sense el bloqueig no vegi «lliure» abans que l'edició nova estigui a punt.

    Recuperació d'enregistraments

    Si el motor o l'ordinador cauen mentre s'enregistra, en arrencar el motor busca marcadors .rec a les carpetes de treball i, per a cadascun (RecordingRecovery):

    1. retalla el fitxer fins a l'últim fotograma complet;
    2. treu l'etiqueta Xing/Info, si n'hi ha;
    3. esborra el marcador;
    4. afegeix l'enregistrament a Recents amb l'etiqueta «Recuperat».

    No toca mai un fitxer que un altre procés té obert. OnaBages.Recovery.exe fa el mateix sobre un fitxer o una carpeta, sense obrir l'aplicació. Cap programari protegeix d'un tall de corrent abans del bolcat: es recomana un SAI.

    Dades

    Regles:

    • Tot l'accés a dades persistents passa per un sol mòdul del motor (OnaBages.Engine/Data, sobretot ConfigRepository).
    • Cada fitxer JSON porta schemaVersion. En llegir-ne un d'antic, es converteix (migració).
    • Escriptura atòmica: fitxer temporal + substitució (AtomicFile).
    • Els àudios no es copien mai a la configuració: només se'n guarden les rutes.

    Excepció acceptada: la posició i la mida de les finestres (finestres.json) les desa Electron, perquè s'ha de saber abans de connectar-se al motor. La de la finestra principal es desa per a cada perfil (D-099): la interfície diu a Electron quin és el perfil actiu, i en canviar de perfil la finestra va on era la d'aquell perfil.

Els enregistraments van a la carpeta de treball de cada enregistrador, i l'historial d'enregistraments a Documents\Ona Bages Play\Historial d'enregistraments (o on es configuri).

    El protocol

    • WebSocket a ws://127.0.0.1:<port>/ws?token=<testimoni>, només des del mateix ordinador. Port per defecte: 47800.
    • Missatges JSON amb "v": 1.
    • Ordres (interfície → motor) amb id, i resposta ok o error (amb un codi: bad_params, bad_state, player_error…).
    • Esdeveniments (motor → tots els clients) amb ev, sense resposta.
    { "v": 1, "id": 42, "cmd": "player.play", "player": "1" }
{ "v": 1, "id": 42, "ok": true, "result": { … } }
{ "v": 1, "ev": "meters", … }

    Les ordres s'agrupen per àmbit: engine.*, devices.*, player.*, playlist.*, recorder.*, recording.*, cue.*, settings.*, editor.*, profile.*, explorer.*, processing.*. La llista completa, amb els paràmetres i les respostes, és a docs/protocol.md.

    Com afegir una ordre

    Exemple real: recordings.clear (netejar Recents).

    1. Protocol: anota-la a docs/protocol.md (paràmetres, resposta, errors) en el mateix canvi que el codi.
    2. Motor: a Protocol/CommandRouter.cs, una línia al switch de les ordres ("recordings.clear" => RecordingsClear(msg)) i el mètode que llegeix i valida els paràmetres. Un valor no vàlid llança BadParamsException, que es converteix en l'error bad_params. La lògica va a la classe que toca (aquí, RecordingList.Clear), no al router.
    3. Prova: a OnaBages.Tests, crida router.Handle("{ … }") i comprova la resposta, també amb paràmetres no vàlids.
    4. Interfície: request('recordings.clear', { includeUnsaved }) des del panell. L'estat nou no el llegeix de la resposta: arriba amb l'esdeveniment corresponent i el store el reparteix.
    5. Si es desa alguna cosa nova, passa per ConfigRepository, amb camp opcional o migració.

    La interfície

    • HTML + Bootstrap 5 (tema fosc) + JavaScript pur amb mòduls ES. Sense React, sense TypeScript, sense empaquetadors. JSDoc i // @ts-check per comprovar tipus.
    • Seguretat: contextIsolation: true, nodeIntegration: false i una política de contingut (CSP). La pàgina només accedeix al sistema pel que exposa preload.js (window.onabages): diàlegs de fitxers, mostrar a l'Explorador, obrir l'editor, aquesta ajuda…
    • Flux de dades: engine-client.js (connexió WebSocket) → store.js (còpia de l'estat, omplerta amb state.get i els esdeveniments; avisa amb esdeveniments del DOM) → un mòdul per panell a js/ui/, que escolta el store i envia ordres. Cap panell guarda estat propi de l'àudio.
    • Editor: editor.html en una finestra pròpia, amb la seva connexió al motor (js/editor/).
    • Estils: colors i mides en variables CSS i en rem, perquè el zoom ho escali tot. Els estats es mostren amb color + icona + text. Les accions que interrompen demanen confirmació.
    • Ordre dels panells (js/ui/panel-order.js, D-105): arrossegament HTML5 natiu des de la nansa .panel-handle, amb un tipus propi per a cada classe de panell (application/x-obp-panel-player / -recorder), de manera que un reproductor no es pot deixar anar sobre un enregistrador ni interfereix amb l'arrossegament de pistes. L'ordre es desa al perfil (ui.playerOrder / ui.recorderOrder) i s'aplica amb la propietat CSS order: els panells no es treuen mai del document. Les dreceres F1–F6 van per la posició (orderedIds).
    • Procés principal (main.js): arrenca el motor, crea les finestres i en recorda la posició, fa créixer la finestra amb el panell lateral, i atén les peticions de preload.js.

    Decisions clau

    DecisióPer què
    C# + NAudio en lloc de C++ (D-002)Molt menys risc per a un sol desenvolupador; errors clars.
    JavaScript pur + Bootstrap (D-003)Tecnologia coneguda, sense passos de compilació.
    Motor i interfície separats, per WebSocket (D-004)La interfície pot caure sense aturar el so; el motor es pot provar des del navegador.
    JSON en lloc de SQLite (D-005)Fàcil de copiar, exportar i depurar; capa de dades preparada per migrar.
    MP3 directe en un sol fitxer (D-006, D-021)Estalvi de temps i d'espai; fitxer vàlid en tot moment gràcies als fotogrames independents i el bolcat cada 2 s.
